# Audit du projet — novembre 2026

Périmètre : code, workflows, réglages GitHub, docs et plans (y compris les changements prévus
dans `docs/plans/`). Audit de structure et de configuration, pas une revue ligne à ligne.
État audité : `main` au 2026-11-10, plus les branches non mergées listées plus bas.

## Verdict

Le projet est solide et crédible comme portfolio. Il n'est pas encore une plateforme « à la
demande » : ajouter une plateforme veut dire écrire une stack à la main. C'est l'axe principal.

## Sécurité

### Ce qui tient
- Aucune clé : OIDC GitHub, state sans clé d'accès (`shared_access_key_enabled = false`),
  Foundry avec `local_auth_enabled = false`, AKS sans comptes locaux et en Azure RBAC.
- Deux identités CI : `plan` en lecture seule, `apply` derrière l'approbation de
  l'environnement `prd`, dont le workflow vérifie la protection.
- Actions GitHub épinglées par SHA, modules AVM épinglés par commit, lock files commités.
- Secret scanning et push protection actifs sur le dépôt.
- Policies préventives ALZ et FinOps ; Key Vault en RBAC avec purge protection.
- Revue des droits faite et documentée (`docs/runbooks/brownfield-lab.md`).

### Constats, par gravité

| # | Constat | Preuve | Conséquence |
|---|---|---|---|
| 1 | `main` n'est pas protégée | API GitHub : « Branch not protected », aucun ruleset | Le passage par PR et plan relu repose sur la discipline. Flux suit `main` : un push direct se déploie sur le cluster sans approbation quand le lab tourne |
| 2 | Rien ne met à jour les versions épinglées | Ni Dependabot ni Renovate ; mises à jour de sécurité Dependabot désactivées | Providers, modules, actions et charts vieillissent en silence |
| 3 | Aucune NetworkPolicy | Rien dans `gitops/` ; Kyverno seulement prévu | Tout pod parle à tout pod |
| 4 | Pas de détection de dérive | Seul `lab-down` est planifié ; le plan des PR du bootstrap tourne sans refresh | Un changement manuel dans Azure passe inaperçu |
| 5 | Endpoints publics : state, Key Vault, ACR, API AKS, Foundry | `public_network_access` activé | Connu et documenté ; traité en partie par `docs/plans/ai-landing-zone.md` |
| 6 | User Access Administrator à la racine pour `apply` | Bootstrap | Connu ; cible : RBAC Administrator avec condition ABAC |
| 7 | Pas de `SECURITY.md` ni de `CODEOWNERS` ; `infra/bootstrap/state.tf` renvoie à un `docs/adr` inexistant | Arborescence | Détails visibles pour un relecteur |

Correctif du constat 1 : PR obligatoire, check `terraform-pr` requis, force-push interdit.
Seul sur le dépôt, pas d'approbation par un tiers, mais le passage par PR et CI devient réel.

## Innovation

Actuel plutôt qu'innovant : les briques sont standard (ALZ, AVM, Flux, Workload Identity).
Ce qui distingue le projet :
- FinOps préventif avec un coût mesuré (2,43 € en octobre 2026) ;
- cycle `lab-up` / `lab-down` ;
- runbook brownfield qui documente aussi les erreurs.

La console de coût en direct (`ai-gateway`) et les règles firewall en données iraient dans le
même sens ; elles ne sont pas livrées.

## Axes d'amélioration

### Terraform en entreprise
- Constat : sept configurations racines à plat, aucun module maison, aucun `terraform test`,
  `azpl` et `prd` en dur.
- Extraire deux ou trois modules versionnés par tag et testés : socle de landing zone, spoke
  réseau, identité de charge.
- Garde sur les destructions à l'apply, détection de dérive planifiée, Renovate.

### GitOps
- Constat : un cluster, une branche, un dépôt, pas de locataires.
- Structure `clusters/<nom>/` et `tenants/<équipe>/` : namespace, RBAC et source Flux par
  équipe (le multi-tenancy de l'extension Flux est déjà actif).
- NetworkPolicies en refus par défaut, Kyverno, images épinglées par digest et mises à jour
  par PR automatique, alertes Flux remontées sur les commits.

### Plateforme à la demande
- Cible : un fichier de demande = une plateforme (`platforms/<nom>.yaml` : propriétaire,
  budget, taille réseau, options AKS, IA, web).
- Une PR produit : subscription, spoke raccordé au hub, fichier de règles firewall, identités
  fédérées, budget, clé de state, pipeline, locataire GitOps.
- Le vending de subscriptions existe dans `infra/landing-zone` ; il reste à généraliser ce que
  `lz-aks` et `lz-web` font à la main, et à prévoir le décommissionnement.
